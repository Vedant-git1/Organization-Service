# ADR 0002: Canonical Contract Integration and Security Boundaries

## Status

Accepted. Supersedes the "adapter assumptions" paragraph of ADR 0001.

## Context

ADR 0001 recorded that the Resolve contract documents were not present in this
repository when the service was founded, so authentication, authorization, and
internal service authentication were implemented behind replaceable adapters
using local mechanisms. The canonical Resolve contracts
(`Documentation/Contracts/*.md`, `Documentation/Schemas/*.md`,
`Documentation/General/*.md`) are now in the repository and the adapters have
been reconciled with them.

This ADR records the resulting decisions and, explicitly, the one requirement
that remains **BLOCKED / CONTRACT NOT AVAILABLE**.

## Decisions

### 1. A separate Organization Service owns tenant identity

`organizations` is the root of tenant ownership: every other tenant-owned table
in the platform foreign-keys to `organizations.id` (FR-ORG-04, FR-TEN-01). Tenant
provisioning and the `ACTIVE`/`SUSPENDED` lifecycle are platform-level
operations, not user-facing ones, so they belong in a service whose only
responsibility is that boundary. Other services call the internal lookup APIs;
they never connect to this database
(`Documentation/Schemas/03_Organization_Service_Schema.md` §2: "Only Organization
Service may directly connect to this database").

### 2. Stack

Node.js 20, TypeScript, Express, MySQL 8.x, Prisma, Zod, Redis, Pino, Vitest,
Supertest, OpenAPI 3.0.3 with Swagger UI, Docker, npm.

The service is already delivered as an independently deployable Node/TypeScript
repository and the established contract-facing behaviour (validation, error
shape, logging) is implemented in that stack. Rewriting it would be an
unjustified architectural change. Request flow is unchanged:
`Route → Middleware → Controller → Service → Repository → Prisma → MySQL`.

### 3. MySQL 8.x via Prisma

The original Resolve documents describe PostgreSQL. MySQL 8.x is the recorded
choice for this repository (ADR 0001) and is what `docker-compose.yml`,
`prisma/schema.prisma`, and the committed migration target. The owned schema is
identical in either engine:

```text
organizations(id CHAR(36) PK, name VARCHAR(255), slug VARCHAR(100) UNIQUE,
              status VARCHAR(20) CHECK IN ('ACTIVE','SUSPENDED'),
              created_at TIMESTAMP, updated_at TIMESTAMP)
```

Consequences that were handled explicitly because of MySQL:

- **UUID generation.** PostgreSQL's `gen_random_uuid()` has no direct MySQL
  equivalent in the migration, so `id` is generated by Prisma
  (`@default(uuid())`) and stored as `CHAR(36)`.
- **Timestamps.** PostgreSQL `TIMESTAMPTZ` becomes `TIMESTAMP(0)`; the service
  serialises them as ISO-8601 UTC strings, matching the contract examples.
- **Uniqueness under concurrency.** Duplicate slugs are prevented by the database
  unique index (`organizations_slug_key`), not by the application check.
  `OrganizationService` performs a pre-check for a friendly early 409 and
  additionally translates Prisma `P2002` to `409 ORG_SLUG_TAKEN`, so a race
  between check and insert still produces the canonical error. Covered by live
  concurrency tests.
- **Case-insensitive collation.** `utf8mb4_unicode_ci` makes the list `name`/`slug`
  filters case-insensitive, matching the intent of an administrative search.

Schema changes remain migration-only (`prisma migrate`), per NFR-DATA-03.
